# 站点通用骨架与主题设计令牌方案

日期：2026-05-19

## 背景

TailwindScore 当前处于 Phase 1 基线阶段，已经具备最小可运行的 WordPress + WooCommerce 主题结构，但站点通用骨架与样式系统仍然偏轻：

- 头部、主导航、页脚、搜索体验只有基础结构，尚未形成可复用的站点级模板能力
- Tailwind CSS 目前仅作为构建工具使用，缺少统一的主题令牌来源
- WooCommerce 默认样式已经由主题接管，但主题内尚未建立完整的商城语义令牌体系
- 模板层未来如果直接堆叠原子类，容易重新走向结构分散、后期难维护的状态

本方案的目标，是在不回到 Bootstrap/jQuery 模式的前提下，为 TailwindScore 建立一套清晰、轻量、可扩展的站点骨架与设计令牌基础。

## 目标

1. 完善站点通用头部、导航、页脚和搜索体验，使主题具备可直接复用的基础站点壳层
2. 建立统一的主题设计令牌配置，作为 Tailwind、CSS 组件层和局部前端交互的共同来源
3. 保持模板层语义清晰，PHP 模板主要消费通用类名，而不是直接堆叠大量 Tailwind 原子类
4. 为 WooCommerce 页面提供独立但兼容全站主题系统的语义令牌，支撑商城页面统一风格
5. 为后续主题换肤、暗色模式、品牌色替换和商城样式细化保留演进空间

## 非目标

本轮方案不包含以下内容：

- 不在本轮重建完整视觉稿或营销型首页
- 不引入 Bootstrap、jQuery 或额外 UI 框架
- 不把模板层改造成高度参数化的组件治理体系
- 不在本轮追求多主题运行时切换
- 不在本轮定义复杂的 design system 文档站

## 设计原则

### 1. 主题令牌优先

设计令牌先服务主题层，而不是先服务某一个模板文件。

主题中的颜色、字体、间距、圆角、阴影、容器宽度、表单尺寸、按钮尺寸、WooCommerce 状态色等，都应先在统一配置中定义，再由 Tailwind、CSS 组件和局部交互层消费。

### 2. 模板只消费语义类名

PHP 模板中的主要职责是结构和语义，不应在标记中堆叠大量原子类，例如：

- `mx-auto max-w-7xl px-4 py-10`

这类布局细节应沉淀为通用类名或站点组件类，由 CSS 层统一承接。

但出于主题开发效率与模板可读性的平衡，模板层允许直接使用少量布局型 Tailwind utility，前提是它们只解决布局、响应式显隐或极少量局部覆盖，不承担视觉风格定义。

### 3. Tailwind 是实现手段，不是模板书写方式

Tailwind CSS 在本项目中主要承担以下职责：

- 作为设计令牌的消费层
- 为组件样式提供底层能力
- 为主题提供可裁剪、可控的实用类基础

但模板层不以“直接堆叠原子类”为主要开发模式。

建议明确约束如下：

- 允许直接进入 PHP 模板的 utility：`container`、`grid`、`flex`、`gap`、响应式列数或跨度、对齐类、`hidden` / `block` / `lg:hidden` / `lg:block`、少量 `order-*`、`col-span-*`、`sticky`
- 不直接鼓励进入 PHP 模板的 utility：颜色、字体、按钮视觉、表单视觉、卡片视觉、WooCommerce 业务状态视觉

也就是说，布局可以直接用 utility，视觉风格仍优先沉淀到 tokens、语义类和组件样式层。

### 4. WooCommerce 仅保留少量业务语义令牌

商城页面与普通内容页共享一套基础设计语言。WooCommerce 不应单独建立一整套结构令牌，大部分布局、表单、边框、阴影、间距和状态表现都应优先复用全局令牌与通用组件类。

只有少量具有明确商城业务含义的值，才值得单独提炼为 WooCommerce 语义令牌，例如：

- 价格
- 库存状态
- 促销标记

像购物车摘要、账户导航、商品卡片、表格、通知条等结构样式，默认直接消费全局令牌，而不是再各自上升为独立 token。

### 5. 轻量优先，避免过度抽象

配置层必须足够稳定，但不能一开始就做成复杂的运行时主题引擎。

本阶段选择“单一令牌真源 + Tailwind/CSS 共享”的做法，而不是引入多层动态主题系统。

同时，只有满足以下条件的值，才应提升为 token：

- 会跨多个组件复用
- 未来存在换肤或品牌替换需求
- 调整频率较高，值得集中管理

一次性区域实现参数不应默认上升为全局令牌。

## 响应式断点

### 令牌数值（唯一真源：`config/theme-tokens.ts`）

| 名称 | 宽度 | Tailwind 前缀 | 组件 CSS 媒体查询 |
|------|------|---------------|-------------------|
| `sm` | `40rem` | `sm:` | `@media (width >= 40rem)` |
| `md` | `48rem` | `md:` | `@media (width >= 48rem)` |
| `lg` | `64rem` | `lg:` | `@media (width >= 64rem)` |
| `xl` | `80rem` | `xl:` | `@media (width >= 80rem)` |
| `2xl` | `96rem` | `2xl:` | `@media (width >= 96rem)` |

构建时会同步输出：

- `@theme` 中的 `--breakpoint-*`，供 Tailwind 工具类消费
- `:root` 中的 `--ts-breakpoint-*`，供文档与运行时引用

**禁止**在组件样式中手写与上表不一致的 `rem` 断点；调整断点只改 `theme-tokens.ts`，并同步更新组件 CSS 中对应的 `@media (width >= …)`（勿使用 `@media (--ts-up-*)` / `@custom-media`，Vite 开发模式下可能不被展开，导致桌面样式整块失效）。

**禁止**在 `@media` 条件中使用 `var(--ts-breakpoint-*)`（浏览器普遍不支持在媒体查询内解析自定义属性）。

### 设备与样式分层约定

采用 **移动优先（mobile-first）**：无媒体查询的默认样式只服务 **低于 `md`（&lt; 48rem）** 的视口，即手机端。

| 视口区间 | 约定 |
|----------|------|
| **&lt; `md`** | 手机端：单列、抽屉/叠层导航、全宽控件等 |
| **`md`～`lg` 以下** | 大屏手机、小平板；仅在需要与手机区分时增加 `md:` 或 `@media (--ts-up-md)` |
| **`lg` 及以上** | 桌面主断点：站点壳层（如 inline 导航、页头布局）默认在此切换 |
| **`xl` / `2xl`** | 按页面需要渐进增强：列数、间距、侧栏、超宽屏留白等，**不必**全站每个组件都写满 |

**设计基准**：桌面视觉稿以 **`2xl`（96rem / 1536px）** 为主要参考画布；**实现**仍从手机默认样式写起，通过 `min-width` 向上叠加，而不是把无媒体查询的样式写成「默认 PC / 2xl」再用 `max-width` 往下覆盖。

### 消费方式

1. **PHP 模板（少量布局 utility）**  
   使用 Tailwind 响应式前缀，例如 `lg:hidden`、`lg:block`。数值与上表一致，由 `tailwind.config.ts` 的 `screens` 映射自令牌。

2. **组件 CSS（`app.css`、`woo.css` 等）**  
   使用与令牌一致的现代区间语法，例如：

   ```css
   @media (width >= 64rem) {
     /* 桌面布局，对应 lg */
   }
   ```

   数值须与 `themeBreakpoints` 保持一致；改令牌时同步改对应 `@media` 条件。

3. **`sm`**  
   在「低于 `md` 即为手机」的前提下，`sm` 仅用于 **手机区间内** 的细调（如横屏略加间距），不另建一套与「手机/桌面」平行的设备体系。

### 与站点壳层、商城的关系

- **Header / 主导航**：移动壳 &lt; `lg`，桌面 inline 导航 ≥ `lg`（与当前实现一致）。
- **WooCommerce**：结账/账户等可在 `lg` 启用多列；商品列表网格可在 `md` / `xl` 按需加分列，无需与 header 使用同一断点档位。
- **容器宽度**（`--ts-layout-container: 72rem`）：在 `lg`～`2xl` 视口内居中；`2xl` 主要用于限制内容区过宽与两侧留白，而非要求所有 PC 组件都包在 `2xl:` 下。

## 推荐方案

本项目采用“独立主题令牌文件 + Tailwind/CSS/TS 共同消费”的方案。

### 核心结构

建议目录如下：

```text
config/
  theme-tokens.ts
src/css/
  app.css
  woo.css
  tokens.css
  components/
    site-header.css
    navigation.css
    footer.css
    search.css
tailwind.config.ts
```

### 各文件职责

#### `config/theme-tokens.ts`

作为设计令牌唯一真源，定义精简的全局核心令牌（含响应式断点）、少量全局语义令牌，以及有限的 WooCommerce 业务语义令牌。断点由 `buildThemeTokenCss()` 同步为 `@theme` 与 `:root` 变量；组件 CSS 中的 `@media (width >= …)` 须与 `themeBreakpoints` 手动保持同值。

#### `tailwind.config.ts`

只负责从 `theme-tokens.ts` 读取令牌，并映射到 Tailwind 可消费的主题项，不再直接承载所有业务语义。

#### `src/css/tokens.css`

将关键令牌输出为 CSS 自定义属性，供组件层和 WooCommerce 样式层复用。

#### `src/css/components/*.css`

承接站点通用语义类名，例如：

- `ts-site-header`
- `ts-nav`
- `ts-site-footer`
- `ts-search-panel`

模板层只使用这些语义类，不直接重复布局细节。

#### `src/css/woo.css`

承接 WooCommerce 元素与主题设计令牌的映射，包括按钮、表单、表格、通知条、账户页、购物车和结账基础布局。

## 统一配置文件内容规划

本项目中的配置文件，不追求覆盖每一个组件或每一个区域的实现细节，而是优先承载真正需要复用和可替换的设计令牌。

### 1. 基础令牌

用于定义整个主题的共性视觉语言：

- 字体族：正文、标题、等宽
- 字号阶梯：`xs`、`sm`、`base`、`lg`、`xl`、`2xl` 等
- 行高阶梯
- 字重阶梯
- 字间距
- 断点：`sm`、`md`、`lg`、`xl`、`2xl`（见上文「响应式断点」）
- 容器宽度：窄内容区、标准内容区、宽内容区

### 2. 空间系统

用于统一页面区块和组件密度。这里以刻度和层级为主，不把每个区域的具体尺寸都收进配置：

- 基础间距刻度
- 区块上下留白
- 卡片内边距
- 面板内边距
- 表单行间距
- 列表项间距
- 导航项间距

### 3. 视觉令牌

用于统一组件质感与层次：

- 圆角：小、中、大
- 阴影：轻、中、重
- 边框宽度
- 边框颜色
- 焦点环颜色
- 焦点环宽度
- 过渡时长
- 过渡缓动

### 4. 颜色系统

用于统一基础配色结构。建议以少量核心色和语义色为主，再由组件层消费：

- 页面背景
- 面板背景
- 卡片背景
- 文本主色
- 次级文本色
- 弱化文本色
- 分隔边框色
- 主品牌色
- 品牌悬停色
- 强调色
- 链接色
- 反白文字色
- 状态色：成功、警告、错误、信息

### 5. 组件语义令牌

用于统一站点基础控件。这里只保留确实会跨组件复用的语义，而不是为每一个组件状态单独建 token：

- 主按钮
- 次按钮
- 幽灵按钮
- 危险按钮
- 输入框
- 文本域
- 选择器
- 卡片
- 标签/徽章
- 弹层遮罩与面板

### 6. WooCommerce 业务语义令牌

WooCommerce 层只保留少量真正具有业务含义的语义令牌：

- 价格色
- 划线原价色
- 库存状态色：有货、低库存、无货
- 促销徽章色
- 评分星级色

如果商城通知条直接采用全局状态色，则不需要再单独建立 WooCommerce 通知色令牌。

商品卡片、购物车摘要、结账区块、账户导航、表格、数量输入等结构样式，默认直接复用全局颜色、间距、边框、圆角、阴影和表单令牌。

### 7. 站点骨架实现关注项

站点通用头部、导航、页脚和搜索体验仍然需要明确设计关注点，但这些内容默认属于组件或区域实现，不全部提升为全局 token：

- Header 结构、层级与吸顶策略
- Header 与导航的背景、边框和交互状态
- 下拉菜单面板的背景、边框和阴影
- 页脚区块层级、标题样式与信息密度
- 搜索表单、搜索面板和结果列表的交互与状态表现

只有当这些值满足复用性高、后期可替换、需要跨组件共享时，才再提升为正式 token。

## 站点通用骨架范围

### 头部

头部应承担以下基础职责：

- 品牌展示
- 主导航入口
- 搜索入口
- WooCommerce 关键入口预留位，例如购物车或账户
- 移动端可折叠导航基础结构

本阶段目标是先建立稳定结构与通用类名，不急于扩展过多营销内容。

### 导航

导航应形成桌面端与移动端都可用的基础模式：

- 桌面端横向主导航
- 当前项高亮
- 子菜单基础面板样式
- 移动端展开/收起交互

交互层不引入 jQuery 依赖。

对于小型界面状态，允许评估引入 Alpine.js，但只限站点壳层和轻量交互，不作为复杂业务逻辑框架。

### 页脚

页脚应具备最小但完整的站点能力：

- 多列 widget/菜单区域
- 版权信息区
- 次级导航或辅助链接区预留

页脚不追求复杂视觉，而强调信息整齐、布局稳定、适合作为基础主题复用。

### 搜索

搜索体验建议拆分为两层：

1. 全站基础搜索表单
2. 可增强的搜索面板或覆盖层体验

本阶段优先保证：

- 统一输入与按钮样式
- 合理的空状态
- 清晰的键盘焦点状态
- 与站点头部结构兼容

如果后续扩展搜索覆盖层，应继续复用统一站点骨架与设计令牌，而不是额外建立独立视觉系统。

## 小交互技术边界

本项目的小交互分为两类：

### 1. 适合 Alpine.js 的轻量交互

如果项目后续选择引入 Alpine.js，它应只负责贴近模板、状态简单、界面导向的小交互，例如：

- 移动端菜单开关
- 下拉菜单展开与收起
- 搜索面板或搜索覆盖层开关
- Accordion
- Tabs
- Modal 或 Drawer 的开合状态
- 点击外部关闭、ESC 关闭等轻量行为

这类交互的特点是：状态局部、与模板结构强绑定、逻辑简单、以 UI 开合和切换为主。

### 2. 继续由 TypeScript 承担的交互

以下内容仍应优先交给 TypeScript：

- WooCommerce 业务流程增强
- 需要较多状态同步的前端逻辑
- 商品页较复杂的交互
- Cart / Checkout 持续演进的行为逻辑
- 跨模块事件较多的交互

因此，本方案对 Alpine.js 的结论不是“全面引入”，而是“可选引入，且只服务站点壳层的小交互”。

## Token 提升规则

为了避免配置膨胀，本项目采用以下判断标准：

适合进入 `theme-tokens.ts` 的值：

- 跨多个组件复用
- 明显服务主题换肤或品牌替换
- 可以作为稳定的基础风格控制项

不应默认进入 `theme-tokens.ts` 的值：

- 单个区域的一次性尺寸
- 单个组件的局部实现参数
- 只在一个模板里出现一次的布局细节

例如，主色、辅助色、中性色、间距刻度、圆角尺度、阴影尺度、字体体系适合成为 token；而 header 高度、搜索面板宽度、页脚版权区高度等值，默认更适合作为组件实现的一部分。

同样地，`container`、`grid`、`flex`、`gap`、`hidden` 这一类布局 utility 允许直接出现在 PHP 模板中；但一旦涉及颜色、字体、表单、卡片、按钮和 WooCommerce 业务视觉，就应优先回到 token 与组件样式层。

## 与 WooCommerce 的结合方式

WooCommerce 主题整合建议遵循以下顺序：

1. 先统一全站骨架和基础控件
2. 再统一商城基础元素样式，例如按钮、表单、通知、表格
3. 再细化商品列表、单品、购物车、结账、账户页等具体模板

这样可以避免一开始就对单个商城模板做局部优化，导致后面又回头重做基础令牌。

## 实施优先级建议

第一阶段建议先覆盖以下范围：

1. 站点头部
2. 主导航
3. 页脚
4. 搜索表单与搜索面板基础
5. 主题令牌配置层
6. Tailwind 与 CSS 变量映射
7. WooCommerce 基础元素样式对齐

第二阶段再进入：

1. 商品归档页细化
2. 单品页细化
3. 购物车与结账布局细化
4. 账户页结构细化

## 主要权衡

### 为什么不把所有内容直接写进 `tailwind.config.ts`

因为项目未来要服务 WordPress 模板、WooCommerce 模板、CSS 组件层和局部 TypeScript 交互。只把所有令牌堆在 Tailwind 配置里，后期会让共享语义变差，配置也会迅速膨胀。

### 为什么不直接在模板中堆 Tailwind 类

因为这是主题，不是一次性页面。主题需要稳定的结构语义和复用能力。模板层长期堆叠原子类，会让站点骨架和 WooCommerce 结构越来越分散，后续替换主题色、调整密度、做统一改版都会变重。

### 为什么仍然保留 Tailwind

因为 Tailwind 仍然是高效的底层实现工具，它适合承载令牌映射、组件实现和最终产物裁剪。只是本项目中，Tailwind 不作为模板书写的唯一界面。

## 风险与约束

- 如果令牌命名过于贴近某个页面或单个区域，会削弱全站复用性
- 如果组件类名过度细分，会重新走向复杂组件治理
- 如果 WooCommerce 结构样式被过度 token 化，会让配置层膨胀且难以维护
- 如果模板层重新开始大量堆叠原子类，方案价值会被迅速稀释

## 结论

TailwindScore 的合理方向，不是把 Bootstrap 机械替换成 Tailwind，也不是把 jQuery 机械替换成 TypeScript，而是借这个重建窗口，建立一套更适合 WordPress + WooCommerce 基础主题的轻量结构：

- 模板负责结构
- 主题令牌负责统一设计语言
- Tailwind 负责令牌映射与组件实现
- TypeScript 负责必要交互
- WooCommerce 在统一主题层下获得稳定、可扩展的商城表现

这将作为下一步实施计划的设计依据。
